Telegram ⇄ Claude Code — setup guide
How it works Setup Memory Safety
Self-hosted · single desktop · no cloud relay

Text a Telegram bot. Your desktop runs Claude Code.

A small Python bridge keeps a full Claude Code session alive on your machine. You message a bot from your phone; Claude works in your real folders with your real tools, then answers in chat. Nothing is proxied through a third-party server — Telegram carries the messages, and the work happens where your files are.

Python 3.10+ No pip installs Windows · macOS · Linux ~$0.02–0.35 per turn

01How it works

Four moving parts, and one design decision that matters.

1

2

3

4
Reply arrivesAnswer, files, live progress

Why not just spawn claude -p per message?

Because it is expensive. Each fresh headless launch re-primes the entire system prompt, all tool definitions and every MCP tool schema. Measured on a one-word reply: ~91k uncached input tokens, roughly $0.46 in Anthropic pricing terms, for the word “hi”.

So the bridge keeps one long-lived claude process per chat and talks to it over the stream-json protocol: 

claude -p --input-format stream-json --output-format stream-json --verbose

Your turns go in as newline-delimited JSON on stdin; assistant, system and result events come back on stdout. A result event ends the turn. The second turn of the same conversation then costs ~170 input tokens instead of 91,000, because the prompt cache is warm.

Conversation state lives in that child process's own session. If it dies, the bridge relaunches with --resume <session_id>, so a crash does not erase the thread. After 30 idle minutes the process is shut down and resumed on your next message.

02What you need

  • A desktop that stays on while you want to reach it. Sleep equals silence — the bridge cannot answer through a sleeping machine.
  • Python 3.10+. Nothing else; the bridge uses only the standard library.
  • Claude Code installed and already logged in on that desktop. Run claude once in a terminal and complete any login before wiring the bot up.
  • A Telegram account to talk to @BotFather and create the bot.
  • Optionally, an Anthropic-compatible endpoint instead of an Anthropic subscription — see the last section.
Check first

If claude does not run by itself in a terminal, the bridge will not fix that. Get a normal interactive session working first — same account, same shell context.

03Setup, start to finish

About ten minutes, most of it waiting for your first message to arrive.

Step 1 — get the code

git clone <this-repo-url> telegram-bridge
cd telegram-bridge

No pip install, no virtualenv, no build step. If python --version says 3.10 or newer, you are done here.

Step 2 — make a bot with BotFather

  1. In Telegram, open @BotFather.
  2. Send /newbot, choose a display name, then a username ending in bot.
  3. Copy the token it returns, shaped like 123456789:AA…. That token is the entire credential. Anyone holding it controls your bot.

Step 3 — first run

With no config.json present, the launcher drops into setup:

run-bridge.bat          # Windows
python bridge.py --setup  # anything else

It will:

  1. Ask for the bot token and verify it against Telegram (wrong token fails immediately, before anything is written).
  2. Write .env with TELEGRAM_BOT_TOKEN=….
  3. Wait up to three minutes for you to message the bot, and learn your numeric Telegram user id from that message.
  4. Write config.json with you as the only allowed user, and a working directory defaulted to the folder the bridge sits in — or to a sibling DSprojects folder when one exists. Edit it if that is not where you want Claude working.
Sanity check

python bridge.py --check validates the token, the claude command, the working directory and the allowlist, then exits without starting the poll loop. Run it before every change of config.

Step 4 — send it something

Message the bot. Anything that is not a slash command is a prompt. While a turn runs you get a live status message that lists the tools being used and updates in place, then a footer like 6 tool calls · 42s · $0.031.

Send a photo or a document and it lands in inbox/; the local path is handed to Claude with your prompt, so “what's wrong with this screenshot?” just works.

04The config that matters

Everything lives in config.json. These are the fields worth understanding.

FieldWhat it does
allowed_user_ids The real gate. Numeric Telegram ids. The bridge refuses every message from anyone else and refuses to start at all if the list is empty.
default_cwd Where Claude starts. Everything is relative to this unless you /cd.
allowed_roots Confines /cd and /send to these directories. Empty means no confinement.
skip_permissions true = full tool access, nothing asks for confirmation. false = anything needing approval is auto-denied and fails cleanly. See Safety.
setting_sources Leave empty so sessions inherit your user, project and local settings — which is what makes your CLAUDE.md, hooks, skills and MCP servers apply over Telegram.
max_budget_usd_per_turn Hard per-turn ceiling in dollars. null is uncapped. Set a number if you want a safety net.
idle_session_timeout_sec Shut the Claude process down after this much idle time (default 1800). The conversation is remembered and resumes on your next message.
max_queue How many of your messages may pile up per chat before new ones are refused.
append_system_prompt Extra instructions for every turn. The shipped default is tuned for phone-sized answers — short, no file dumps, make an assumption instead of asking mid-task.
Edit carefully

config.json is read at start. Restart the bridge after changing it. Keep the bot token in .env, not in this file — both are gitignored, but only one of them should ever be opened in an editor by accident.

05Start it at logon (optional)

powershell -ExecutionPolicy Bypass -File install-startup.ps1
powershell -ExecutionPolicy Bypass -File install-startup.ps1 -Status
powershell -ExecutionPolicy Bypass -File install-startup.ps1 -Uninstall

On Windows this registers a scheduled task that runs the launcher in a hidden window at logon, allows battery start, restarts up to three times, and has no execution time limit — it is meant to run for the whole session. On other platforms, run python bridge.py under systemd, launchd, or tmux.

One instance only

Two bridges both call getUpdates and eat each other's messages — the symptom is messages that randomly vanish. Check for a running bridge.py before starting another, including before kicking the scheduled task by hand.

07Memory keeping

The part that makes it feel like one long-running assistant instead of a stranger each morning.

There are three separate layers, and they solve different problems. Confusing them is why most “give my bot a memory” attempts end up either useless or dangerous.

LayerLives inSurvivesHolds
Session The child claude process Process restarts and 30-min idle shutdowns (via --resume); lost on /new The conversation itself — what you said two turns ago
Memory .claude/memory/ on disk Everything, including /new and a new machine Durable facts: decisions, measurements, preferences, dead ends
Instructions CLAUDE.md Everything Standing rules about how to work — including how to use memory

The bridge passes setting_sources through, so a headless session started from Telegram loads the same CLAUDE.md and the same memory directory as a session you open by hand in that folder. Memory therefore works identically whether you are at the desk or on your phone.

The layout

your-project/
├── CLAUDE.md                 the rules — read at the start of every session
└── .claude/
    └── memory/
        ├── MEMORY.md         index: one line per note, always loaded
        ├── budget-format.md  one fact per file, kebab-case name
        ├── deploy-server.md
        └── rule-verify-paths.md

MEMORY.md is the index and is the only file guaranteed to be in context at the start. That is the whole trick: the index is cheap to load, and it tells the model which individual notes are worth opening for the question at hand. Keep it to one line per note.

What one note looks like

---
name: deploy-server
description: production box is 10.0.0.12, deploys go through the staging tunnel
metadata:
  type: project
---

Deploys run from `~/sites/www` on 10.0.0.12. The staging tunnel must be up first —
`./tunnel.sh up` — or the rsync silently lands in the wrong tree.

Related: [[backup-schedule]]
typeUse for
userWho you are — role, expertise, standing preferences
feedbackCorrections and confirmed approaches, with the why. These are the highest-value notes you will write.
projectOngoing work, goals, constraints that are not derivable from the code or git history
referencePointers outward — URLs, dashboards, ticket numbers

The rules, as a block you can paste

Memory without rules rots: duplicates pile up, relative dates go stale, and confident wrong notes outlive the facts they described. Put this in CLAUDE.md — it is what turns a folder of notes into a memory system.

# Memory

Durable notes live in `.claude/memory/`. `MEMORY.md` is the index and is read at the
start of every session. Read it first; open only the notes it points at.

## Writing memory
- Save durable facts without being asked — decisions, measurements, preferences,
  dead ends someone would otherwise repeat.
- One fact per file, kebab-case name, with frontmatter:

  ---
  name: short-kebab-slug
  description: one line, used to decide relevance during recall
  metadata:
    type: user | feedback | project | reference
  ---

  the fact, then "Why:" and "How to apply:" for feedback and project notes.

- Link related notes with [[their-name]].

## Maintenance
- Update the existing note instead of writing a near-duplicate.
- Delete notes that turn out to be wrong; a stale note is worse than none.
- Convert relative dates to absolute ones ("next Friday" -> 2026-11-06).
- After writing or changing a note, fix its line in MEMORY.md.
- Do not record what the repo already records: structure, history, obvious code facts.

## Trust
- A note is a claim, not proof. Re-read the file, or the doc, before asserting a
  path, flag, version or number that came from memory.
- Never store secrets, tokens, keys, or passwords in memory files.
The one that bites

A memory written today is confidently re-asserted in three weeks. If the note names a file, a flag or a function, the model must check that it still exists before recommending it — otherwise you get a helpful answer about code that was refactored away. The “a note is a claim” line above is doing more work than the rest of the block combined.

Keeping it healthy

  • Start the index at zero. Ten sharp notes beat a hundred vague ones; recall quality tracks index quality.
  • Prune on a schedule. Once a month, read MEMORY.md top to bottom and delete anything you would not act on.
  • Back it up. It is plain Markdown — commit it, or put it in a synced folder. This is also how you move the whole setup to a new machine.
  • Keep it out of public repos. Notes about your projects, clients and machines are not for sharing, even when the code is.

08What it costs

This runs a full agent with all your MCP servers attached, so it is not free and not trivial. Measured range on a desktop with a handful of MCP servers: ~$0.02–$0.35 per turn, depending on how much work Claude does and how well the prompt cache hits. Cached turns are cents; a turn that reads forty files is not.

  • Set max_budget_usd_per_turn to a number for a hard ceiling.
  • Lower idle_session_timeout_sec if sessions linger overnight.
  • A cheaper model for routine work is the biggest lever — invoke it with /model.
  • /status shows cumulative session spend.

09Safety — read this before you enable it

The consequence, plainly

With skip_permissions: true, anyone who can message this bot can run commands on your desktop as you, with no confirmation. A prompt asking Claude to delete files, push a repo or send mail is simply carried out.

That setting exists because a headless run cannot answer a permission prompt — anything needing approval would otherwise fail rather than run. Set it to false if you would rather have prompts auto-denied; the boundary is blunt but real.

What actually protects you

  • allowed_user_ids — the only real gate. The bridge refuses to start with it empty.
  • allowed_roots — confines /cd and /send.
  • The token in .env — treat it as a password. If it leaks, revoke it with @BotFather.

What does not

  • A hard-to-guess bot username. Bots are discoverable; that is obscurity.
  • Group-chat privacy. Anything posted in a group is visible to everyone in it.
  • “Nobody knows the name.” Assume someone can find it and add your id only if you recognise it.

Never commit

.env, config.json, state.json, bridge.log and inbox/ — the token, your chat state, and everything Claude touched. The shipped .gitignore already covers them. Keep it that way.

10Troubleshooting

“Not authorized”, and no reply from Claude

By design. The bot replies with the sender's numeric id — add it to allowed_user_ids and restart. Never add an id you do not recognise.

Nothing happens when I message it

Check bridge.log next to bridge.py. If the process is not running, the launcher will say why. On Windows, check the scheduled task state with install-startup.ps1 -Status.

Claude exits unexpectedly

The bridge auto-resumes with --resume, so just send your next message. Repeated exits usually mean a broken hook or an MCP server that hangs at startup — the log keeps the child's last stderr lines.

Formatting looks wrong

Telegram HTML rejects an entire message if one entity is malformed. The client retries as plain text when that happens; raw **asterisks** mean the fallback fired.

Memory grows without limit, or is wrong

That is a rules problem, not a storage problem. Re-read the Maintenance block in Memory keeping: one fact per file, update instead of duplicating, delete wrong notes, fix the index line every time.

The desktop slowly runs out of memory (Windows)

Older builds leaked a claude.exe on every session teardown: the CLI sits behind an npm shim, so the process that matters is a grandchild, and terminating the shim orphaned it with a dead stdin pipe — unreachable, still holding memory. The current claude_session.py kills the whole process tree (taskkill /F /T /PID on Windows, a process group on POSIX) and selftest.py pins the fix with a live wrapper/grandchild test.

If it ever regrows, the shape to look for is a claude.exe whose parent is gone. Confirm the bridge's own tree has no claude.exe child before touching anything, then kill the leaked ones by explicit PID.

“Not logged in” even though you are

Usually a stale daemon lock rather than an account problem: a dead claude.exe still holds daemon.lock, so claude daemon stop answers “no daemon running” and does nothing. Kill the process holding the lock. Watch out for integrity levels — a daemon started from an elevated shell cannot be reached or killed from a normal one, and the reverse.

11Optional: a different backend

If you are not using an Anthropic subscription, point Claude Code at any Anthropic-compatible endpoint.

Set these in the env block of ~/.claude/settings.json rather than only in shell variables, so the daemon, background agents and bridge sessions all read the same file:

{
  "env": {
    "ANTHROPIC_BASE_URL": "https://your-endpoint.example/anthropic",
    "ANTHROPIC_AUTH_TOKEN": "…",
    "ANTHROPIC_MODEL": "your-model-name",
    "ANTHROPIC_DEFAULT_OPUS_MODEL": "your-model-name",
    "ANTHROPIC_DEFAULT_SONNET_MODEL": "your-model-name",
    "ANTHROPIC_DEFAULT_HAIKU_MODEL": "your-model-name"
  }
}

Two traps worth knowing, both learned the hard way:

Unrecognized model = early compaction

If Claude Code has no catalog entry for your model id, it assumes a 200k window and auto-compacts roughly five times too early, throwing away most of your usable context. The warning reads “Claude Code doesn't recognize the model …”. Fix it with CLAUDE_CODE_MAX_CONTEXT_TOKENS set to your endpoint's real window — for a 1M model, 1048576.

The dollar figure is a lie

total_cost_usd in a result event is computed from Anthropic's price table, so against a third-party endpoint it is meaningless — and cumulative per session, not per turn. Judge cost from token counts and your provider's published rates. If the provider has cheap and expensive hours, schedule heavy work accordingly.

Also: never commit ~/.claude/settings.json once it holds a token, and never put a credential in a chat message, an issue, or a memory file.
